The **AI Deal Scoping Assistant** converts customer requirements into a reviewed solution package containing: 

* Approved requirements and functional scope 
* Cloud architecture 
* Data, integration, and AI strategies 
* Delivery workstreams and estimates 
* Risks, assumptions, dependencies, and open questions 
* Requirement traceability and quality findings 

However, a reviewed solution package is not yet an execution plan. 

Delivery teams must still determine: 

* What work needs to be completed 
* How the work should be divided 
* Which activities depend on each other 
* What can run in parallel 
* Which Topcoder operating model is best suited for each unit of work 
* What information is needed before execution can begin 

This challenge is to build a browser-accessible **Deal-to-Challenge Graph Engine** that transforms the supplied deal-scoping JSON packages into an execution-ready Directed Acyclic Graph, or DAG, of connected delivery nodes. 

Each node must represent a meaningful unit of work and be classified into one of Topcoder’s three operating models: 

1. **Flexible Talent** 
2. **Challenge** 
3. **Private Pod** 

A deal may use one operating model throughout or combine different operating models across the graph. 

The application must preserve traceability from the imported requirements and architecture to every generated node. 

The final product should feel like an intelligent deal-to-execution compiler, not a generic task generator, project board, static flowchart, or single AI prompt that produces a list of challenges. 

 
## Relationship to the AI Deal Scoping Assistant 

The **AI Deal Scoping Assistant** answers: 

What should be built, how should it be designed, and what effort may be required? 

The **Deal-to-Challenge Graph Engine** answers: 

How should the approved solution be divided, sequenced, and delivered using Topcoder’s operating models? 

This process begins after the deal-scoping package is available. 

The Deal-to-Challenge Graph Engine should be implemented as a separate application or process for this challenge. Integration with the AI Deal Scoping Assistant or the wider Topcoder platform may be considered in the future but is not required here. 

The imported deal package may contain: 

* Reviewed requirements 
* Functional capabilities 
* Architecture components and flows 
* Data domains and integrations 
* AI use cases 
* Delivery phases and estimates 
* Risks, assumptions, dependencies, gaps, and questions 
* Quality findings 
* Traceability relationships 

The engine must use and preserve these relationships when generating the delivery graph. 

 
## Challenge Goal 

Build an AI-powered delivery-compilation experience that enables users to: 

* Import and validate the supplied deal-scoping JSON packages 
* Normalize the imported package into a shared execution model 
* Review blockers, assumptions, gaps, and open questions 
* Assess whether the package is ready for execution planning 
* Divide the solution into meaningful delivery nodes 
* Classify each node as Flexible Talent, Challenge, or Private Pod 
* Explain why each operating model was recommended 
* Build a dependency-aware DAG 
* Identify parallel work, execution waves, and the critical path 
* Generate an execution package appropriate to each node’s operating model 
* Trace every node to imported requirements and architecture components 
* Modify nodes, operating models, or dependencies and review the impact 
* Validate the graph before operational handoff 
* Export the graph and model-specific execution packages 

The generated graph is an internal planning aid. The application must not automatically recruit talent, launch a challenge, build a private pod, approve funding, or commit delivery timelines.

## Topcoder Operating Models 

This specification provides only the context needed to classify work correctly. 

Participants are not expected to implement Topcoder’s internal sales, staffing, talent-search, community-management, or delivery operations. 

### 1. Flexible Talent 

Use Flexible Talent when the work is best completed by one or more specific resources with clearly defined skills. 

Flexible Talent is generally suitable when: 

* Required skills and roles are already known 
* The work can be assigned to specific individuals 
* The client or delivery team will manage the work directly 
* Competitive exploration is not required 
* The need is primarily specialist expertise or additional capacity 
* The work can fit within an existing delivery team 

Examples include: 

* Adding a frontend engineer to an existing product team 
* Assigning a data engineer to a defined pipeline backlog 
* Providing a cloud specialist for a focused configuration task 
* Providing a QA engineer for an established test plan 
* Assigning a technical expert for an assessment 

A Flexible Talent node should describe: 

* Required roles 
* Required skills 
* Seniority or experience 
* Expected duration or capacity 
* Responsibilities 
* Start dependencies 
* Required access and environment 

### 2. Challenge 

Use the Challenge model when the work benefits from open participation, multiple submissions, alternative approaches, competition, or community creativity. 

A Challenge is generally suitable when: 

* Multiple approaches or perspectives are valuable 
* Deliverables can be evaluated using clear criteria 
* The scope can be packaged independently 
* Broader community participation adds value 
* Participants do not need unrestricted access to sensitive information 
* The expected result is measurable and reviewable 

Examples include: 

* UX concept exploration 
* Data-science model development 
* Computer-vision solution exploration 
* Design work 
* Algorithm or optimization work 
* A clearly bounded application component 
* Independent testing or quality work 

A Challenge node should describe: 

* Challenge objective 
* Participant context 
* Deliverables 
* Evaluation criteria 
* Acceptance conditions 
* Input assets 
* Required technologies or skills 
* Dependencies 
* Confidentiality limitations 
* Expected review process 

### 3. Private Pod 

Use Private Pod when the work requires a coordinated, vetted team to own a complex or sensitive delivery area. 

A Private Pod is generally suitable when: 

* Multiple technical roles must work together 
* Architecture and implementation are closely connected 
* Continuous technical leadership is required 
* Multiple components are strongly coupled 
* The work requires restricted access 
* Confidentiality or endpoint controls apply 
* Sustained delivery ownership is required 

Examples include: 

* Delivering a multi-component enterprise integration 
* Building a regulated AI workflow 
* Implementing a cloud platform foundation 
* Modernizing a tightly coupled application area 
* Building a coordinated data platform 
* Delivering work requiring architecture leadership and multiple engineers 

A Private Pod node should describe: 

* Pod objective 
* Required roles and skills 
* Technical-leadership requirement 
* Component ownership 
* Delivery responsibilities 
* Security and access requirements 
* Coordination dependencies 
* Expected duration 
* Definition of completion 
 
## Operating-Model Classification Principles 

Every executable DAG node must have one recommended primary operating model: 

* flexible-talent 
* challenge 
* private-pod 

The engine must not assume that every node should become a Challenge. 

A deal may produce: 

* A graph using one operating model 
* A graph combining two operating models 
* A mixed graph using all three operating models 

The engine should consider: 

* Scope clarity 
* Required roles and team size 
* Need for technical leadership 
* Degree of collaboration 
* Component coupling 
* Suitability for competitive delivery 
* Value of multiple approaches 
* Security and confidentiality 
* Data sensitivity 
* Duration and continuity 
* Client management capacity 
* Acceptance measurability 
* Need for broad community participation

For each node, the engine should recommend the most suitable operating model and explain the reason in simple terms. 

If the work does not fit cleanly into one operating model, the engine should: 

* Recommend splitting the work into smaller nodes, or 
* Define a clear handoff from one operating model to another 

Each node should contain: 

* Recommended primary operating model 
* Classification rationale 
* Classification confidence 
* Alternative operating models, where applicable 
* Source evidence supporting the decision 
* User override history, where applicable 

Users must be able to override the recommended operating model. The override and its rationale must be recorded as a user-reviewed decision.

Where information is missing, the engine should create a discovery or clarification node rather than inventing requirements, contracts, security details, or acceptance conditions.

## Functional Requirements 

### 1. Deal Package Ingestion and Validation 

The application must directly accept all four supplied JSON files. 

The importer must extract applicable: 

* Requirements 
* Assumptions, gaps, questions, risks, and dependencies 
* Capabilities, modules, and workstreams 
* Architecture components and flows 
* Data domains and integrations 
* AI use cases 
* Delivery estimates 
* Quality findings 
* Traceability links 

The importer must validate: 

* JSON structure 
* Required sections and identifiers 
* Duplicate and dangling identifiers 
* Existing blockers and quality findings 
* Unresolved questions and assumptions 
* Stale sections 
* Architecture or platform conflicts 
* Missing estimation inputs 

The original imported package must be preserved separately from the normalized execution model. 

**Constraints** 

1. Missing information must be reported and must not be silently invented. 
2. Every imported item used by the graph must preserve its source identifier. 

### 2. Source-Package Maturity Assessment 

The engine must classify the imported package as: 

* **Execution Candidate** 
* **Review Required** 
* **Discovery Required** 
* **Blocked** 

The assessment should consider: 

* Existing quality status 
* Critical questions and gaps 
* Unconfirmed assumptions 
* Missing contracts 
* Missing architecture or security decisions 
* Estimate confidence 
* Stale sections 

Incomplete packages should generate discovery, clarification, or approval work before affected implementation nodes. 

**Constraints** 

1. Critical missing information must reduce readiness or create a blocking discovery node. 
2. An incomplete package must not be presented as fully ready for execution. 

### 3. Delivery Node Generation 

The engine must decompose the solution into meaningful execution nodes. 

Possible work categories include: 

* Discovery 
* UX or design 
* Frontend 
* Backend or API 
* Integration 
* Data engineering 
* AI implementation 
* Cloud and DevOps 
* Security 
* Testing 
* Documentation 
* Deployment 
* Technical review

Each node must contain: 

* Node ID 
* Title and objective 
* Work category 
* Scope 
* Source identifiers 
* Inputs and deliverables 
* Acceptance conditions 
* Dependencies 
* Required skills 
* Complexity and effort 
* Risks and assumptions 
* Blocking status 
* Operating-model recommendation 
* Classification rationale 
* Provenance 
* Readiness status 

Users must be able to: 

* Edit, add, or remove nodes 
* Split or merge nodes 
* Approve or reject AI-generated nodes 
* Mark nodes as blocked or review-required 

**Constraints** 

1. Every node must be grounded in imported information or an approved user decision. 
2. Unsupported or generic nodes must not be treated as ready for execution. 

### 4. Operating-Model Classification and Execution-Package Generation 

Every executable node must be classified as: 

* flexible-talent 
* challenge 
* private-pod

The engine must evaluate the work characteristics and explain the recommendation. 

**Flexible Talent Package** 

A Flexible Talent package should include: 

* Required roles and skills 
* Seniority or experience 
* Duration or capacity 
* Responsibilities 
* Start dependencies 
* Required access and environment 
* Readiness status 

**Challenge Package** 

A Challenge package should include: 

* Challenge objective 
* Business and technical context 
* Deliverables 
* Evaluation criteria 
* Acceptance conditions 
* Input assets 
* Required technologies or skills 
* Dependencies 
* Confidentiality limitations 
* Expected review process 
* Readiness status 

**Private Pod Package** 

A Private Pod package should include: 

* Pod objective 
* Required roles and skills 
* Technical-leadership needs 
* Component ownership 
* Delivery responsibilities 
* Security and access requirements 
* Coordination dependencies 
* Expected duration 
* Definition of completion 
* Readiness status

**Constraints** 

1. Every node must have exactly one primary operating model and an explainable rationale. 
2. The engine must support mixed-model graphs and must not assume that every node should be a Challenge. 
3. If work requires multiple active models, the engine should recommend splitting the node or defining a clear handoff. 
4. Nodes must not be marked ready when the information required by the selected operating model is missing. 

### 5. DAG Construction and Dependency Management 

The engine must connect approved nodes into a Directed Acyclic Graph. 

Each edge must include: 

* Source node 
* Target node 
* Dependency type 
* Rationale 
* Source identifiers 
* Blocking status 
* Required input or handoff 

The engine must identify: 

* Cycles 
* Orphan nodes 
* Self-dependencies 
* Duplicate or invalid edges 
* Blocked nodes 
* Entry and terminal nodes 
* Parallel and sequential work 

The engine must calculate: 

* Execution waves 
* Critical path 
* Earliest start opportunities 
* Graph-level effort and duration 
* Operating-model distribution by wave 

**Constraints** 

1. A graph containing a cycle must not be marked ready. 
2. Every dependency must include a source-backed or user-reviewed rationale. 

### 6. Change Impact and Quality Validation 

Users must be able to modify: 

* Node scope 
* Work category 
* Operating model 
* Dependencies 
* Source assignments 
* Effort 
* Acceptance conditions 
* Blocking status 

After a change, the engine must identify: 

* Affected and unaffected nodes 
* Changed dependencies 
* Invalidated execution packages 
* Operating-model changes 
* Changed execution waves 
* Critical-path changes 
* Effort or duration changes 
* Newly blocked or newly ready nodes 

The quality gate must check: 

* Source coverage 
* Unsupported nodes 
* Duplicate or overlapping scope 
* Missing inputs or acceptance conditions 
* Operating-model classification completeness 
* Missing classification rationale 
* Model-to-work mismatch 
* Missing model-specific package information 
* Cycles and orphan nodes 
* Invalid dependencies 
* Blocked or stale nodes 
* Critical-path completeness 

Quality statuses must include: 

* Ready 
* Review Required 
* Blocked

**Constraints** 

1. Every node must have a valid operating model before the graph can be marked Ready. 
2. Changes must preserve approved and unaffected nodes and execution packages. 

### 7. Visualization and Export 

The application must provide: 

* Deal summary 
* Package-maturity status 
* Node inventory 
* Visual DAG 
* Dependency view 
* Execution waves 
* Critical path 
* Blocked-node view 
* Operating-model summary 
* Effort and duration summary 
* Traceability 
* Quality-gate result 
* Model-specific package previews 

The graph should visually distinguish: 

* Flexible Talent nodes 
* Challenge nodes

* Review-required nodes 

The application must export at least:

## Success Definition 

A successful submission allows an evaluator to: 

1. Import all four supplied JSON packages. 
2. Review package maturity and blockers. 
3. Generate grounded execution nodes. 
4. Classify every executable node as Flexible Talent, Challenge, or Private Pod. 
5. Understand the reason for every classification. 
6. Generate a graph using one or multiple operating models. 
7. Review model-specific execution packages. 
8. Detect cycles, orphan nodes, and invalid dependencies. 
9. Review execution waves and the critical path. 
10. Override an operating model and review the impact. 
11. Preserve unaffected nodes. 
12. Run the quality gate. 
13. Prevent incomplete work from appearing ready. 
14. Export source-traceable graph JSON and model-specific packages. 
15. Run the complete workflow without paid AI access.
